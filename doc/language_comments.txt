##Unsorted rules (should go to main language document)

###Argument promotion rules for constant folding (binary arithmetic, calculate-constants.c):

    The common type of a binary arithmetic expression is chosen by the first matching rule
    (operands are then converted to it, and the operation is evaluated in that type):

      1. complex double - if either operand is complex double, OR one is complex float and
         the other is double or a 64-bit integer (int64/uint64)
      2. complex float - if either operand is complex float
      3. double - if either operand is double, OR one is float and the other is a 64-bit integer
      4. float - if either operand is float
      5. int64 - if either operand is int64, OR one operand is signed and the other is
         uint32 or uint64 (the wider signed type can represent all uint32 values; a signed/uint64
         mix goes to int64 because there is no wider signed type)
      6. uint64 - if either operand is uint64 (both are unsigned at this point)
      7. int32 - if either operand is signed (any signed type, or a signed/small-unsigned mix)
      8. uint32 - otherwise (both operands are unsigned and at most 32 bits)

    Notes / rationale:
    - float combined with a 64-bit integer promotes to double (float cannot represent all
      int64/uint64 values exactly); the same rule lifts complex float to complex double
    - Small integers (int8..int16, uint8..uint16) promote to int32/uint32 - sub-32-bit
      arithmetic is always done at machine width, matching C integer promotion
    - Mixed signed/unsigned where the unsigned type is narrower than the signed result is
      still exact (uint32 always fits in int64); uint64 mixed with signed also goes to int64
      (may clamp large uint64 values - this is reported as a conversion warning)
    - Constant folding reports an ERROR on: integer division/modulo by zero, integer overflow
      (signed and unsigned + - *), and non-arithmetic operands. It reports a WARNING (but still
      folds, producing the result) when an operand conversion is rounded or clamped.
      Floating-point division by zero is allowed (produces inf/NaN per IEEE 754); a WARNING is
      emitted when both operands are finite but the result overflows to infinity or is NaN
      (e.g. 1e38 * 1e38, 0.0 / 0.0) - operands that were already infinite/NaN do not warn.
    - Shifts (<< >>) require integral operands; the shift count is read as int32 regardless of
      the left operand width, and the result type follows the (promoted) left operand.
    - Logical && || require boolean operands and are folded separately (calculate_logic);
      they are not arithmetic promotions.

##Member and static functions (adopted rules, supersede rough edges 12, 16, 17)

###Function values and signatures
A function value's signature is always its declared argument list - there is no
signature negotiation at call sites.
- Ad-hoc (per-instance) member functions capture this through the closure - the
  receiver is bound at creation, not passed at call time.
- Class methods (pre-built by C code - scripts cannot modify classes) have an
  implicit this parameter: they are created once and must serve every instance,
  so the receiver is passed at call time.

###Declaration context
- A lambda is static by default; the static prefix forces a plain function with
  exactly the declared signature in any context.
- Expression { Sentences } is a member block: the head is evaluated once, the body
  is executed with this bound to it, and unqualified names resolve to the head's
  properties first, then attributes (the block is an explicit convenience context;
  the strict ./-> separation applies to the operators). New names are installed as
  attributes (compile-time error if the head does not implement AZAttributeList).
  The head type must be known at compile time (resolver error otherwise).
- A class-valued head gives a class context. Classes are pre-built (C code) and
  cannot be modified from scripts: unqualified names resolve to existing class
  properties or are compile-time errors, and assignments target existing writable
  class properties or are errors - no new methods or properties can be installed.
  Lambdas created in a class context capture the class namespace (bare names
  resolve to class properties) but keep exactly the declared signature.
- obj.name = lambda is sugar for obj { name = lambda; } - the dot propagates
  context to the right, symmetrically with how it propagates the receiver to a
  call. obj.name = static lambda stores a plain function instead.
- static { Sentences } evaluates the body in static context (this == NONE).

###Call resolution (no probing, decided by what the name resolves to)
- obj.name(args) where name is a class function-table method - method call,
  this == obj.
- obj.name(args) where obj is a class and name is a static function property -
  static call (args).
- obj.name(args) / obj->name(args) where name is a data property or attribute
  holding a function value - fetch, call with the declared signature (args); no
  receiver injection. Stored closures and stored static functions work identically.
- The instance-vs-class type of the left operand decides member-vs-static,
  statically whenever the type is known. Static functions are reached via the
  class: obj.class.name(args) (requires obj.class to yield the class of obj).
- (obj.name)(args) and f = obj.name; f(args) fetch the value and call it plainly -
  any indirection ends the this-propagation.
- Extracting a class method (f = obj.method) materializes a bound closure
  (this == obj), so callbacks never silently lose their receiver.

###C-facing function properties (boundary adaptation)
- Function properties defined in C code have fixed contract signatures, often
  with the object as the leading argument (e.g. onButtonDown(AosoraWidget,
  uint32, uint32)) - C callers have no other way to know which object fired.
- In a member context (member block, obj.prop = lambda), a lambda assigned to a
  function property may use either the full contract signature or the shortened
  form with the leading receiver argument dropped.
- Full form: the closure is stored as-is. this is still captured (member
  context), but the receiver argument is the one passed by the caller - use the
  parameter, not this, for generic handlers shared between objects.
- Shortened form: the runtime stores a lightweight adapter (an AZFunction
  implementation) that references the script closure, exposes the contract
  signature, and on invocation drops the receiver argument and forwards the
  rest. this is captured by the closure as usual; during the call the receiver
  passed by the caller is not available to the lambda at all - it only has its
  captured this (for the common mywidget.onButtonDown case the same object).
- Signatures matching neither form are errors - compile-time when the target
  type is known, runtime at the store otherwise.
- Attributes (AZO-native) never adapt - the closure is stored as itself.
- Reuse: otherwidget.onButtonDown = mywidget.onButtonDown reads the adapter and
  stores it; calls still invoke mywidget's member closure (this == mywidget).
  This is correct - it reuses mywidget's handler logic.

###. and -> (properties vs attributes)
- Properties/functions are defined in C code: the list and types are immutable,
  but the content can be modified (depending on the property).
- Attributes exist only for instances implementing AZAttributeList - first and
  foremost AZActiveObject subclasses (most game objects derive from it).
- . resolves properties/functions only (the current attribute fallback is
  deprecated).
- -> resolves attributes only.
- Neither implies a calling convention.

##Closure model and memory management (adopted rules)

###Storage model
- Closure: parent captures including this (read-only snapshots), static variables
  (read-write), link to the shared datablock, link to code (may be shared, may be
  JIT-optimized for one closure).
- Shared datablock: function-level constants (read-only) and shared variables
  (read-write). Owned by the program code plus all live closures of the lambda;
  freed when the program and all its closures are gone. Closures can escape the
  script (stored in attributes of long-lived objects) - then the datablock
  outlives the script, held by the escaped closure.
- A new closure is created on every evaluation of the lambda expression. The
  optimizer may reuse a closure only if it has no non-constant captures and no
  static variables; closure identity (===) of such lambdas is unspecified.
- static variables: per-closure, initialized at closure creation (arbitrary
  expressions allowed).
- shared variables: per lambda declaration site (not per enclosing invocation),
  constant-expression initializers only (the datablock exists before any closure).
- All AZActiveObject captures (including this) are weak - closures never extend
  ActiveObject lifetimes. Rationale: an ActiveObject's meaningful life is its
  membership in the ownership tree; an object kept alive only by a closure is not
  updated/rendered/simulated - a zombie. A dead capture reads as (typed) null;
  member access throws unless the function opted in with the nullsafe flag
  (rough edge 15). Non-ActiveObject captures (numbers, strings, arrays, closures)
  are by-value/strong - closure-to-closure cycles are impossible by construction.
- Keeping an object alive is done by anchoring, not by capture strength: a local
  anchors for the enclosing frame's lifetime (create-configure-attach window);
  a persistent anchor is an attribute of an object that outlives the closure's
  uses (objects own data, closures are behavior).
- weak variables (AZWeakReference, AZActiveObject only) read as null after the
  referent's shutdown. AZWeakReference needs fixed-address storage (the ref
  struct's address is registered as listener data; the stack compacts), so weak
  is valid at program/script scope - a compile-time error on function locals.
- Mutable cross-closure state goes through shared variables or object attributes;
  captured variables are snapshots.

###Memory model
- All collectible cycles pass through an AZActiveObject edge: closure-to-closure
  cycles are impossible by construction (snapshot captures are temporal - a closure
  can only capture what already exists at its creation), and the only mutable
  closure-holding slots are object attributes and program-rooted shared/static
  storage.
- Cycles through attributes are broken by uniformly weak ActiveObject captures
  (member closures, listeners, back-pointers) and recursive shutdown clearing
  attributes.
- Shared/static storage is program-rooted, not a cycle participant: an object kept
  alive by a shared variable is kept alive by the alive script (usually tied to a
  game object) - same semantics as a global, freed at script unload.

###Implementation checklist
- AZOCompiledFunction split: closure object (captures, statics, datablock link,
  code link) vs shared datablock (constants, shared variables) vs code/program.
- Replace the bound flag + GET_PROPERTY "bound" skip-jump + AZO_TC_BIND with an
  unconditional MAKE_CLOSURE n_captures opcode.
- Resolver: tag lambda context (static / member / class); all AZActiveObject
  captures (including this) are bound as weak captures.
- static declarations in function scope: allocate in closure, initialize at
  creation; shared declarations: allocate in datablock, constant initializer.
- weak qualifier: AZWeakReference slots for AZActiveObject references; reads
  produce null after shutdown (typed null per rough edge 15); compile-time error
  for non-AZActiveObject types and for function locals (fixed-address storage
  required - valid at program/script scope).
- Optimizer: closure reuse only when no non-constant captures and no static
  variables; per-closure JIT code must never migrate to the shared code link.
- Shutdown integration: clearing attributes releases closures; recursive shutdown
  propagates as explicit shutdown calls (never passive refcount drops).
- Property-store adaptation: when storing a function value into a C function
  property, compare signatures - exact contract match: store as-is; leading-
  receiver-dropped match: create and store an adapter (AZFunction implementation;
  references the closure, exposes the contract signature, drops the first
  argument on invoke, forwards the rest); anything else: error (compile-time if
  the target type is known).
- Verify: no mutable closure-holding container outside attributes and
  program-rooted storage (e.g. arrays in attributes are fine - shutdown releases
  the array, which releases the closure).
- Remove the legacy 'function' keyword path (HAS_FUNCTION_KEYWORD) once scripts
  are migrated.

###Usage guidelines (script code)
- DO attach behavior with member closures: btn.onClicked = () => { ... } - all
  ActiveObject captures (this included) are weak, no cycle possible.
- DO use static int32 n = 0 inside a lambda for per-closure counters (per-button
  click counts, accumulators).
- DO use shared for state common to all closures of the same lambda (rare in
  singleton scripts - a script-scope constant usually suffices).
- DO anchor objects that must stay alive: a local anchors for the enclosing
  frame's lifetime (create-configure-attach window), an attribute of a
  long-lived object anchors persistently. A closure never keeps an ActiveObject
  alive.
- DO dispose objects explicitly and in time - shutdown breaks the attribute edges.
- DO use weak only for script-scope back-pointers (e.g. weak Button other =
  otherBtn;) - it is a compile-time error on function locals.
- DO write C-property handlers in the shortened form: mywidget.onButtonDown =
  (uint32 button, uint32 modifiers) => {...} - this is captured. Use the full
  contract form (AosoraWidget widget, ...) only for generic handlers shared
  between objects, and then use the parameter, not this.
- DON'T expect a captured ActiveObject to be alive inside a closure - reads of
  dead captures are null; member access throws unless the function opted into
  nullsafe. Check for null or anchor the object.
- DON'T rely on closure identity (===) for lambdas without captures/statics - the
  optimizer may cache them.
- DON'T try to mutate captured variables - they are snapshots; use shared or
  attributes for mutable state.

15. Typed null (class valid, instance NULL) - design notes (on hold, not implemented yet):
    - Needed for overload picking: 'null as String' is our analogue of Java's '(String) null' -
      the 'as' operator has to accept it (null is exempt from the instance check)
    - No typed null for value types (dereferencing a value-typed member of null throws)
    - No two typed nulls are ever equal (even to themselves) - typed null is a missing value,
      not a special value (SQL NULL semantics); same for identity ('is' is always false on it)
    - a == null is not a real comparison but isNull(a) (symmetric: null == a), so typed nulls
      compare equal to untyped null
    - As a consequence of non-reflexive equality: sorting and map keys (and anything
      hash/identity-based) are notnull-only and throw on null
    - Method calls on null: static methods are safe; instance methods run with this == null
      but must explicitly opt in with a nullsafe flag (default: throw). Propagation is thus
      controlled per-member at declaration site; UI trees can opt in, secure methods stay safe
    - Untyped null is the 'none' value (a real value), typed null is an absence of value
    - Open: syntax of the nullsafe flag; debug-mode logging of null derefs would help debugging
