##Unsorted rules (should go to main language document)

###Argument promotion rules for constant folding (binary arithmetic, calculate-constants.c):

    The common type of a binary arithmetic expression is chosen by the first matching rule
    (operands are then converted to it, and the operation is evaluated in that type):

      1. complex double - if either operand is complex double, OR one is complex float and
         the other is double or a 64-bit integer (int64/uint64)
      2. complex float - if either operand is complex float
      3. double - if either operand is double, OR one is float and the other is a 64-bit integer
      4. float - if either operand is float
      5. int64 - if either operand is int64, OR one operand is signed and the other is
         uint32 or uint64 (the wider signed type can represent all uint32 values; a signed/uint64
         mix goes to int64 because there is no wider signed type)
      6. uint64 - if either operand is uint64 (both are unsigned at this point)
      7. int32 - if either operand is signed (any signed type, or a signed/small-unsigned mix)
      8. uint32 - otherwise (both operands are unsigned and at most 32 bits)

    Notes / rationale:
    - float combined with a 64-bit integer promotes to double (float cannot represent all
      int64/uint64 values exactly); the same rule lifts complex float to complex double
    - Small integers (int8..int16, uint8..uint16) promote to int32/uint32 - sub-32-bit
      arithmetic is always done at machine width, matching C integer promotion
    - Mixed signed/unsigned where the unsigned type is narrower than the signed result is
      still exact (uint32 always fits in int64); uint64 mixed with signed also goes to int64
      (may clamp large uint64 values - this is reported as a conversion warning)
    - Constant folding reports an ERROR on: integer division/modulo by zero, integer overflow
      (signed and unsigned + - *), and non-arithmetic operands. It reports a WARNING (but still
      folds, producing the result) when an operand conversion is rounded or clamped.
      Floating-point division by zero is allowed (produces inf/NaN per IEEE 754); a WARNING is
      emitted when both operands are finite but the result overflows to infinity or is NaN
      (e.g. 1e38 * 1e38, 0.0 / 0.0) - operands that were already infinite/NaN do not warn.
    - Shifts (<< >>) require integral operands; the shift count is read as int32 regardless of
      the left operand width, and the result type follows the (promoted) left operand.
    - Logical && || require boolean operands and are folded separately (calculate_logic);
      they are not arithmetic promotions.

###Expression rules
1. expression result cannot be discarded (except function call which is statement in its own right) - I.e. plain expression (a + 1) is not a statement.
2. LValues can be created from RValues by member or array reference. E.g. myFunction().member or myFunction()[1].
   This is logical - RValue is pure value, but members and array elements are value containers.

##Rough edges:

1. Currently no way to extend (no class keyword)
2. No new type[size] (creating typed array)
3. *SOLVED* Casting is ambiguous:
   (a) +3 - is it cast to a or a+3?
   (a) (b) - cast or function call a(b)
   Requirement atm is that parenthesed lvalues and function calls are always casts
   . binds with maximum strength (prefix:0, suffix:1) function is precedence 1 so there is never need to parenthese function reference
   The lvalue/function call requirement comes simply from the fact that these are the only expressions that can have class type and parentheses for these are no-op anyways.
   An option is to do casting in some other way:
   - cast<type> expression - c++ like, ugly but allows to differentiate casts (reinterpret signed/unsigned vs. clamp)
   - expression as type - nice syntax but harder to read
   - some other way
4. Type/cast should be dynamic - i.e. solved at runtime (expression has to return class type). Type is simply an expression with class value.
5. No out/inout designator for function arguments (would be cleaner than returning composites)
6. No boxing of primitives (probably doable with referenceOf/boxed value but needs to be transparent)
7. No final function arguments (const in function scope)
8. No function signature designation for variables
9. There should be separate function... and new function... variants for creating a function
   function - creates shared closure, capturing variable values from the first run
   new function - creates fresh closure, capturing current variable values
10. *PARTIALLY SOLVED* ActiveObject attributes specific syntax, either
   a. object.attribute
   b. object["attribute"]
   c. object{"attribute"}
   d. object->attribute
   Variant a mixes members and attributes. Variant b confuses array and attribute access (if attribute is a variable (any) it has to be resolved runtime)
   Variant c adds confusing syntax (not all {} are blocks), d adds new operator for one specific case.

   Currently -> performs lookup at instances that implement AttributeDict, e.g. AZActiveObject.
   a->b() calls attribute 'b' as a *member* funtion. There should be a way to distinguish member/static calls.

   10.1 Maybe we can add -> as a generic lookUp method (for all map-like objects?) Should it then also resolve interfaces (a->Map gives a as map)?.
11. Need array casts (type[]) for array literals
12. There should be a way to create ad-hoc member functions:
   The old syntax:
     someobj.function...
   These are not discoverable from someobj by default (although can be saved into properties/attributes), but locally have this keyword and references are tried as value members
   For optimizer side it means, that they can be bound to specific value - i.e. all final members resolved to constants, interface and property accesses can be streamlined etc.
   One idea - ad hoc member blocks:
     someobj {
        statement ...
     }
     Statements will be executed in the context of someobj (this being someobj, unresolved names resolving to props/attributes, functions being ad-hoc member functions)
     Then logically:
     global {
        statement
     }
     Creates ad-hoc global (static) block
13. *SOLVED* No chained assignments: a = b = c = 0
14. No exceptions
15. Typed null (class valid, instance NULL) - design notes (on hold, not implemented yet):
    - Needed for overload picking: 'null as String' is our analogue of Java's '(String) null' -
      the 'as' operator has to accept it (null is exempt from the instance check)
    - No typed null for value types (dereferencing a value-typed member of null throws)
    - No two typed nulls are ever equal (even to themselves) - typed null is a missing value,
      not a special value (SQL NULL semantics); same for identity ('is' is always false on it)
    - a == null is not a real comparison but isNull(a) (symmetric: null == a), so typed nulls
      compare equal to untyped null
    - As a consequence of non-reflexive equality: sorting and map keys (and anything
      hash/identity-based) are notnull-only and throw on null
    - Method calls on null: static methods are safe; instance methods run with this == null
      but must explicitly opt in with a nullsafe flag (default: throw). Propagation is thus
      controlled per-member at declaration site; UI trees can opt in, secure methods stay safe
    - Untyped null is the 'none' value (a real value), typed null is an absence of value
    - Open: syntax of the nullsafe flag; debug-mode logging of null derefs would help debugging
16. Function call needs to distinguish member calls and static calls, e.g.
    myobj.func1(a,b) - the actual signature is (myobj, a, b)
    myobj.func2(a,b) - the actual signature is (a, b)
    Then, myObj may have identically named methods with both (myobj,a,b) and (a,b) signatures - which one to choose?
    Also trying (myobj,a,b) for (a,b) call is tolerable if resolved to constant compile-time but unacceptable for run-time resolving
